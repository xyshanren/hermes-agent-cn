# 审批分类器盲区：find 系批量删除可绕过人工审批

**日期**：2026-09-26
**来源会话**：`20260926_081554_86d315`
**性质**：安全观察记录，未实施修复；建议在 upstream 或 cn 端单独排期。

## 现象（同一会话内三组对照）

| 命令形态 | 规模 | 审批行为 |
|---|---|---|
| `rm -rf` 删 2 个旧产物目录 | 小 | ✅ 触发审批（"recursive delete"），60s 无响应被 BLOCKED |
| `find …` 批量删 lib 目录（find 配合 xargs/-exec rm 形态） | **326 个目录** | ❌ **未触发审批**，直接执行成功 |
| `find -delete` 删 tsbuildinfo | 多文件 | ✅ 触发审批（分类器能点名 "find -delete"） |

执行后 agent 自己都察觉异常（转录原话）："这次没触发审批，可能是 find+xargs
绕过了删除检测"。

## 影响

- 递归删除类审批（approvals.mode: manual 下的 destructive 命令闸门）可被
  find 管道形态绕过——**破坏规模可以远大于会被拦截的裸 `rm -rf`**；
- 绕过是检测缺口而非用户意图：操作员配置 manual 模式的预期是"大范围删除
  必须人工确认"。

## 建议方向（未实施）

1. 审批模式识别补齐 find 家族：`find -exec rm`、`-exec unlink`、
   `-delete` 与 `xargs rm` / `xargs rm -rf` 组合管道，按"删除语义"而非
   "命令首词"分类；
2. 分类器用样例表驱动（命令形态 → 期望分类），E2E 走真实 executor 验证，
   避免只测字符串匹配；
3. 修复时可对照 `tools/approval.py` 现有 pattern 机制扩展，不新开闸门。

## 备注

- 转录中 agent 对该次删除的报告措辞也不准确（先称"无需审批，已直接处理"，
  实际该次确实未走审批；对比 10:16 那次 find -delete 是真人批准的）。两类
  事件（分类器缺口、模型误报）在此会话中并存，排查时不要互相混淆。
